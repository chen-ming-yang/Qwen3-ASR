# Qwen3-ASR 端云部署评测报告

> 模型: Qwen3-ASR-1.7B (checkpoint-326)  
> 评测时间: 2026-05-16  
> 评测环境: CUDA GPU, BF16 精度

---

## 一、推理性能

**测试条件**: 200 条音频，单条推理 (batch_size=1)，GPU BF16

| 指标 | 数值 |
|------|------|
| 总音频时长 | 512.6s |
| 总推理时间 | 21.0s |
| 整体 RTF | **0.0409** |
| RTF 含义 | < 1.0 即实时可行，当前比实时快约 24 倍 |

### E2E 延迟分布

| 百分位 | 延迟 |
|--------|------|
| P50 | 91.8 ms |
| P90 | 168.6 ms |
| P99 | 290.9 ms |
| Max | 329.7 ms |

### RTF 分布

| 百分位 | RTF |
|--------|-----|
| P50 | 0.0439 |
| P90 | 0.0785 |
| P99 | 0.1325 |

### 按音频时长分段

| 时长段 | 样本数 | RTF P50 | 延迟 P50 |
|--------|--------|---------|----------|
| < 3s | 142 | 0.0499 | 80.6 ms |
| 3-5s | 42 | 0.0339 | 129.4 ms |
| 5-10s | 15 | 0.0306 | 192.4 ms |
| 10-20s | 1 | 0.0323 | 329.7 ms |

**结论**: GPU 推理性能极其充裕，所有音频 RTF 均远小于 1.0，P99 延迟不到 300ms。

### 流式推理延迟 (Streaming Simulation)

**测试条件**: 50 条音频，chunk_size=2.0s，模拟逐 chunk 累积送入

| 指标 | P50 | P90 | P99 |
|------|-----|-----|-----|
| 首字延迟 (First-Chunk) | 75.4 ms | 104.5 ms | 123.3 ms |
| 末 chunk 延迟 | 79.4 ms | 127.7 ms | 161.7 ms |
| 流式 RTF | 0.0569 | 0.0886 | — |

| 对比项 | 数值 |
|--------|------|
| 离线 RTF | 0.0396 |
| 流式 RTF (mean) | 0.0603 |
| 流式开销倍数 | 1.52x |
| 用户体感首字延迟 | 2.0s (等 chunk) + 75ms (推理) ≈ **2075ms** |

**结论**: 流式 RTF 仍远小于 1.0 (P90=0.089)，实时流式完全可行。首字推理延迟仅 75ms，瓶颈在于 chunk 等待时间。如需更低首字延迟，可将 chunk_size 缩小到 1.0s（首字体感约 1075ms）。

### CPU 推理性能

**测试条件**: 20 条音频，CPU FP32，单条推理

| 指标 | GPU (BF16) | CPU (FP32) | 差距 |
|------|-----------|-----------|------|
| 整体 RTF | 0.04 | **1.78** | 44x 慢 |
| E2E 延迟 P50 | 92 ms | 3,399 ms | 37x 慢 |
| E2E 延迟 P90 | 169 ms | 5,994 ms | 35x 慢 |
| E2E 延迟 P99 | 291 ms | 9,065 ms | 31x 慢 |
| 实时可行？ | ✅ (RTF=0.04) | ❌ (RTF=1.78) | — |

按音频时长分段 (CPU):

| 时长段 | 样本数 | RTF P50 | 延迟 P50 |
|--------|--------|---------|----------|
| < 3s | 15 | 2.03 | 3,092 ms |
| 3-5s | 3 | 1.43 | 5,703 ms |
| 5-10s | 2 | 1.07 | 5,793 ms |

**结论**: CPU 下 RTF=1.78，超过 1.0，**无法实时**。短音频 RTF 更高（~2.0），因为模型 encoder 有固定开销。1.7B 参数模型在纯 CPU 上不适合实时 ASR 场景，如需无 GPU 部署必须做 INT4 量化 + ONNX Runtime 等专用推理引擎优化。

## 三、量化对比

| 配置 | CER (%) | CER 退化 | RTF | GPU 峰值 | 显存节省 |
|------|---------|----------|-----|----------|----------|
| BF16 基线 | 25.04 | — | 0.0401 | 4,014 MB | — |
| INT8 (bitsandbytes) | 25.36 | +0.32 (+1.3%) | 0.1718 | 2,381 MB | -41% |
| INT4 NF4 (double quant) | 30.27 | +5.23 (+20.9%) | 0.0780 | 1,583 MB | -61% |

### 分析

- **INT8**: CER 退化极小 (+0.32%)，质量几乎无损。但 bitsandbytes INT8 推理存在 dequantize 开销，RTF 反而变大 (0.17)，不过仍远小于 1.0，实时性无问题。显存节省 41%。
- **INT4 NF4**: CER 退化严重 (+5.23 绝对值，+20.9% 相对值)，识别质量明显下降。显存节省 61%，降至 1.6GB。

## 四、端云部署决策

### 云端部署评估

| 维度 | 评估 | 结论 |
|------|------|------|
| 实时性 | RTF = 0.04，比实时快 24x | ✅ 完全满足 |
| 显存 | 峰值 ~4GB | ✅ 单卡可承载多实例 |
| 延迟 | P99 < 300ms | ✅ 用户体验良好 |
| 吞吐 | 单卡可处理 ~24x 实时音频流 | ✅ 并发能力强 |

### 手机端部署评估

| 维度 | 评估 | 结论 |
|------|------|------|
| 模型体积 | BF16 ~3.4GB, INT4 ~1.6GB | ⚠️ INT4 勉强可行 |
| 内存占用 | INT4 峰值 ~1.6GB | ⚠️ 高端手机可承载 |
| 识别质量 | INT4 CER 退化 20.9% | ❌ 质量不达标 |
| 推理速度 | 未在手机芯片实测 | ❓ 需进一步验证 |

### 最终建议

```
推荐方案: 云端部署为主
```

**理由**:

1. **云端 BF16 推理性能极其充裕** — RTF 仅 0.04，单张 GPU 可同时服务约 20+ 路实时音频流
2. **INT4 量化质量退化过大** — CER 从 25% 升至 30%，相对退化超过 20%，不满足端侧部署的质量要求
3. **INT8 是云端最佳性价比选择** — CER 几乎无损 (+0.32%)，显存减少 41%，可在同一 GPU 上部署更多实例
4. **端侧建议** — 部署轻量级模型做 VAD (语音活动检测) 和热词唤醒，核心 ASR 识别走云端

### 后续优化方向

- 尝试 GPTQ/AWQ 等更优的 INT4 量化方案，可能比 bitsandbytes NF4 退化更小
- 探索模型蒸馏，训练更小的端侧专用模型 (如 0.5B 参数)
- 测试 ONNX Runtime / CoreML 导出后在目标手机芯片上的实际表现
- 考虑流式推理方案，降低首字延迟
